### WishButton usage (WP-01, WP-03)
- Inside an island that already has a `TextProvider` with the `product` catalog:
  `<WishButton productId={p.id} name={p.name} variant="inline" shortLabel />` (BuyColumn) or `variant="tile"` (HomeProductCard).
- As its own island from an `.astro` page:
  `<WishButtonIsland client:visible productId name locale dicts={dictsFor(locale, {product: ['tile'], common: ['error']})} />`
  (default export too). It calls `bag.sync()` on mount and `bag.toggleWishlist` on click (optimistic + rollback, toast on error).

## Differences from VAREL
1. `GET /wishlist` answers `{items, ids}` instead of a bare `Product[]`; move-to-bag answers `{cart, ids}` instead of a bare `Cart`. F2's `bag.sync()` already accepts `{ids}`.
2. New `GET /wishlist/ids` (cheap ids-only read for the header count and hearts).
3. Reads and DELETE never create a visitor row or set a cookie (VAREL upserted the session on GET). Only POST and move-to-bag call `ownerOf`.
4. Cap of 100 saved pieces per owner (409 `wishlist_full`); all reads bounded to 100.
5. Move-to-bag is set-based: one read set + one batch transaction (VAREL ran `addLine` per piece). Same rules: first available variant, 1 unit, merged into an existing line, skipped at stock limit / 99 units / bag line limit; moved pieces leave the wishlist, others stay.
6. Kept VAREL quirk: move-to-bag skips a variant at inventory 0 even when the product allows backorder (one-line change in `planMove` if the owner wants otherwise).
7. "Clear list" removes optimistically in one store update, sends the DELETEs in parallel, then settles on one `GET /ids` read (parallel answers can arrive out of order). No confirmation, as in VAREL.
8. Only published products are listed, counted or moved (also in `/ids`).
