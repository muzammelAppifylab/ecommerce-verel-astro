### Onboarding (`POST /site-api/account/onboarding`)
Called by every sign-in on these pages (password, email code, two-step, register 201) before the redirect,
3 s timeout, errors ignored. Body `{email?, firstName?, lastName?, newsletter?}` from the browser stash, applied
only when `email` equals the signed-in account's. Creates the `CustomerProfile` (names from extras, else
`splitName(users.name)`; locale = request locale; P2002 race → re-read), newsletter upsert `source:'signup'` +
`marketingOptIn` (never unsubscribes), `mergeGuestIntoUser` when a `visitor_id` cookie is present, `welcome`
email via `sendTemplate` once, at profile creation, only for accounts younger than 30 days. Answer
`OnboardingResult {profileCreated, subscribed, merged}` (type already in `src/lib/types/account.ts`).

## Differences from VAREL
- Sign-in is the template's: code-first login (no password needed), 10–128-char passwords (not email name, not
  common), email confirmation before the first sign-in (register answers "check your inbox" for new AND taken
  emails, so `signup.emailTaken` only shows if the owner turns verification off), no "Keep me signed in"
  (refresh is always 30 days sliding), account emails (verify, reset, code) are the platform's relayed English emails.
- Sign-up extras travel via `localStorage` to the first sign-in: confirming on another device loses only the
  newsletter choice (names come from `users.name`).
- Pages are ON DEMAND (`prerender = false`) so `/da/account/...` render localized; login/register/forgot
  `Cache-Control: public, max-age=300`, reset/verify/confirm-email `no-store` + `secretInUrl`.
- Server error texts are mapped to the `auth` catalog by error code; 5xx always shows the localized generic line.
- Newsletter box pre-ticked (VAREL parity) — owner decision: pre-ticked consent is weak under GDPR.
- Not ported (D5): AcceptInvite / staff invites (`auth.invite.*` keys kept, unused).
