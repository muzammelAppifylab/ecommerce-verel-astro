# WP-19 · Orders & returns admin: hand-off

Branch `wp/WP-19` (from `wave0`). Port of VAREL `worker/routes/admin/orders.ts` (orders + returns),
`src/lib/admin/sales.ts` (orders/returns part) and `src/pages/admin/{orders,returns}/*`.

## What was ported

### Server (`/site-api/manage/orders`, `/site-api/manage/returns`)
| Route | Notes |
|---|---|
| `GET /orders` | `CursorPage<AdminOrderRow>`; filters `payment`, `fulfillment` (multi), `from`/`to` (bare `to` inclusive), `q` (≤ 5 words; number, email, account name, profile first/last name, shipping-address name via a bounded tagged `$queryRaw` ILIKE, exact normalized number for digits); sort whitelist `placedAt, number, total, email` (`-` desc), keyset on `(sort, id)` |
| `GET /orders/export.csv` | VAREL `/orders.csv`. Same filters; keyset pages of 100, at most 40 (4,000 orders); VAREL columns; formula-escaped (`csvCell`); `audit(..., 'orders_exported', meta {filtered})` |
| `GET /orders/:number` | `AdminOrder` (F4 `serializeOrder` + customer, staff note, events newest first, returns with amounts). Accepts `24817`, `vrl24817`, ` VRL-24817 ` |
| `PATCH /orders/:number` | VAREL l.181–243: stage follows fulfilment, one "Marked as shipped · carrier tracking" event, tracking/payment/note events (`at = now + i ms`), 409 `order_cancelled` / `order_refunded`; `order_shipped` / `order_delivered` emails after commit |
| `POST /orders/:number/refund` | Nets out refunded returns (amount + units), money FIRST via `contracts.refundOrder(..., 'refund-order-<id>')` outside any transaction, then a conditional `payment: 'Paid'` update (409 `already_refunded` on a race), restock of the remaining physical lines, event "Refunded $x · n items restocked · note"; `order_refunded` email after commit |
| `GET /returns` | `CursorPage<AdminReturnRow>`; `status` multi, `q` (email, order number, `#id`), keyset on `(createdAt, id)` |
| `GET /returns/:id` | `AdminReturn` (items with line names/prices; "Removed item" for deleted lines) |
| `PATCH /returns/:id` | `RETURN_NEXT` transitions (409 `return_transition`, `return_closed`, `order_refunded`, `conflict` on a concurrent change); refund: money first (`refund-return-<id>`), then conditional update + restock of the returned lines + order `Returned`/stage 4 (+ `Refunded` when every physical line is back, shipping refunded then when `refundShipping`); `return_update` email on every status change |

## Differences from VAREL (deliberate)
- Keyset paging + "Load more"; no totals ("25+ orders" from the first page). No page param in the URL.
- Sort whitelist `placedAt, number, total, email` (VAREL also accepted `payment`, `fulfillment`, unused);
  returns sort `createdAt` only. The UI sorts with a `Select` (kit tables have no sortable headers).
- Search uses at most 5 words; address-name lookup capped at 500 ids per word (VAREL 5,000).
- CSV export capped at 4,000 orders (40 keyset pages of 100) and built inside the request (not
  streamed: the request-scoped database client is closed once the handler returns). VAREL: 10,000 in one query.
- Staff note ≤ 2,000 characters (F1 column); VAREL 5,000.
- Returns show `#<id>` (integer ids) instead of VAREL's `…<last 8 of cuid>`.
- Rows: the number cell is the link (kit has no row click).
- Copy: VAREL dialogs said "No email is sent" while the server sent `order_shipped`, `order_refunded`
  and `return_update`. The server behaviour is kept and the copy now says the customer gets that email
  when it is switched on in Settings › Emails. "Mark as paid … No email is sent." is true and kept.
- Order detail shows the customer's checkout note (VAREL admin did not).
- Bulk PATCHes run 5 at a time (VAREL: all at once).
- `stage` is not exposed in the UI (as VAREL); the API keeps it.

## Requests
1. **Integrator / F3** (`tests/integration/manage-areas.test.ts`): it expects `GET /site-api/manage/orders`
   to answer 501 (stub); it now answers 200. Change that expectation to 200 (or drop `orders` from it).
2. **F1 / integrator**: `@@index([totalCents(sort: Desc), id(sort: Desc)])` on `shop_orders` for the
   "Highest/Lowest total" sort; optional GIN trigram indexes on `shop_orders.email`, `number` and
   `(address->>'name')` before the order count reaches the thousands.
3. **WP-22**: a bulk "Mark shipped" of up to 100 orders sends up to 100 `order_shipped` emails: queue
   them within the platform's job-add rate.
4. **WP-11**: confirm `refundOrder` idempotency per `reason` covers both the provider call and the
   `ShopPayment` record (keys `refund-order-<id>`, `refund-return-<id>`), and that a provider failure
   throws a 502 `payment_provider_error` (`HttpError`).
5. **WP-14**: write return `items[].lineId` as numbers (`shop_order_items.id`); digit strings are accepted too.
6. **WP-16**: `navCountsQuery` (`openOrders`, `pendingReturns`) is read by the Orders/Returns tabs; its key
   is under `['admin', 'dashboard']`, so order/return changes here refresh it.
7. **WP-20**: `FilterMenu` (and `selectColumn`, `ConfirmModal`) in `screens/orders/ui.tsx` can be imported
   for the customers list.

## Known gaps
- PATCH `payment` accepts any status and moves no money, stock or discounts (VAREL parity), e.g.
  "Mark as paid" on a Failed order does not take stock again. Flag for I2 / the owner.
- A return refund on a Pending/Failed order is not blocked (VAREL parity); `refundOrder` gives back
  at most what was paid.
- Activity-log summaries come from WP-26's middleware (nothing called here); not verified until WP-26 merges.
- Emails go through the `sendTemplate` stub (logged) until WP-22 merges; refunds through the
  `refundOrder` stub until WP-11 merges.
