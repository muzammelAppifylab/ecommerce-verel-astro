## Differences from VAREL
1. **Bounded scan:** the list derives rows/summary from the 500 most recently active bags (`capped: true` + a Notice when there are more). VAREL loaded every bag. Summary counts are over the scanned bags.
2. **Keyset paging** (`cursor` = `[sortValue, id]`, Load more) instead of page numbers; sort by a `Select` instead of clickable headers; ties broken by id.
3. **Job:** due bags picked in SQL, oldest activity first (VAREL: most recently *updated* window, which could starve old bags); **≤ 8 reminders per run** (VAREL 50) because each reminder queues a `send-email` job (platform add limit ≈ 10/min). "Send due reminders" uses the same cap. The result also carries `outcomes` (incl. `superseded`).
4. **Bulk remind** looks at the selected bags plus their shopper's other bags (siblings) to decide "superseded", not every bag in the store. **Bulk dismiss/restore** is one `UPDATE … WHERE id IN (…)` (raw SQL so `updated_at` is untouched); duplicate ids are de-duplicated silently (VAREL parity).
5. Forced remind clears `dismissedAt` with raw SQL (keeps `updated_at`) and answers the fresh row (siblings of that shopper only).
6. Orders matching for "ordered since" in the LIST uses exact lower-cased emails (index-friendly; checkout stores emails lower-cased). F4's `sendReminder` still checks case-insensitively.
7. The "Send due reminders" hint is visible text under the button (not only a `title`), the status hint is also visually-hidden text for screen readers.
8. `POST /run` and `POST /:id/remind` read and ignore their body: with an unread JSON body the dev runtime (miniflare) failed the NEXT request on the connection (`fetch failed`, 500 without reaching the worker). **Heads-up for every package with body-less POSTs that the portal calls with `body: {}`.**

## Requests
1. **F3 (types, additive):** `AbandonedList.capped?: boolean` and `AbandonedRunResult.outcomes?: Partial<Record<string, number>>`. Today the route returns them and the portal types them locally (`AbandonedPage`, `AbandonedRunReport` in `queries/abandoned.ts`).
2. **F4 (`src/server/lib/abandoned.ts`):** add `requestUrl?: string` to `RemindContext` and pass it to `sendTemplate(…, {requestUrl})` (`sendJob` needs it). `runAbandonedReminders` already receives it (`config.siteUrl` from the job, `c.req.url` from the admin). Also retire or re-point `bagsWithContact`/`dueCarts` (ordered by `updatedAt` only, 100 cap) at `abandoned-scan.ts`; nothing in WP-24 uses them.
3. **F1 (schema):** `email_messages @@index([template, createdAt(sort: Desc)])` for the "Recovered" tile; consider `carts(lower(email))` / `@@index([email])` for `siblingsOf` (insensitive `IN`).
4. **WP-22:** `sendTemplate` must stay queue-safe under the job-add limit (keep the outbox row `queued` and deliver later on `E_JOBS_RATE_LIMITED`): `reminderSentAt` is claimed before sending. Template `abandoned_cart` vars: `firstName` (may be ''), `cartUrl`, `items[{name, meta, qty, total}]`, `itemCount`, `subtotal`, `storeName`, `supportEmail`; outbox rows need `template='abandoned_cart'` and `status` (`failed` excluded from "Recovered").
5. **WP-23:** `PATCH /site-api/manage/settings` must accept a partial `{abandonedCartEnabled}` / `{abandonedCartHours: 1–720}`. The screen invalidates `['manage','settings']` after a change; tell me (or change `ReminderSettings`' caller) if your settings query key differs.
6. **WP-09:** bump `carts.updated_at` when a line is added (keeps the `carts_abandoned_idx` window close to real activity; the scan itself does not depend on it).
7. **WP-11:** store `ShopOrder.email` lower-cased (the list's "ordered since" and "Recovered" match exact lower-cased emails).
8. **WP-26:** the remind response keeps `email` for "Sent an abandoned bag reminder to {email}".
9. **F5 (optional):** a selectable/pressable `Stat` variant and DataTable row selection in the kit; the screen uses a local `button.stat` and a checkbox column meanwhile.
