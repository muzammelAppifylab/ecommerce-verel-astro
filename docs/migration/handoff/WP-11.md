## Differences from VAREL

- **No Stripe SDK**: 5 REST calls on `fetch` (`Stripe-Version: 2026-09-30.endive`, `Idempotency-Key` on create (`order-<id>`) and refunds, 10 s timeout, one retry only for GETs / idempotent POSTs). `constructEventAsync` → own WebCrypto verifier. `STRIPE_API_HOST` (stripe-mock) dropped: tests stub `fetch`.
- Secrets via `config.ownerSecret('STRIPE_SECRET_KEY' | 'STRIPE_WEBHOOK_SECRET')`; publishable key from Settings.
- Newsletter opt-in: `newsletter_subscribers` upsert (`source: 'checkout'`) + `customer_profiles.marketingOptIn` only for the signed-in shopper's own email (VAREL wrote `users.newsletter`).
- Saved address: primary via `findFirst` (no `count()`); skipped when `city` > 100 chars (`addresses.city` is VarChar(100), checkout allows 120).
- Expiry job bounded: 20 oldest orders per run, no new order started after 45 s (VAREL took 100).
- `related.id` in `sendTemplate` is the order NUMBER (contract), VAREL passed the id.
- Event timestamps: the `placed` event now gets the same JS clock as the digital "delivered" event (+1 ms), so they always sort in order (DB `now()` vs JS clock could invert them).
- `cancel` answers 200 `{order, restored}` (F3 stub comment said 204; VAREL parity kept).
- Order prefix read from `getSettings` before `normalizeOrderNumber` (cold-isolate safe).
- No webhook event-id table: every handler is a conditional update (`Pending→Paid`, `Pending→Failed`, `Failed→Paid`) and `charge.refunded` SETS Stripe's running total, so replays change nothing and send no second email.

## Owner setup (for the I1 README)

- Site secrets `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (test keys in staging, live in production); publishable key + provider "Stripe" in Settings → Payments.
- Stripe webhook endpoint `https://<site>/site-api/webhooks/stripe` with events `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `charge.refunded`.
- **Without Stripe configured, checkout is simulated: orders are marked Paid and no money is taken.** The owner must configure Stripe before going live.

## Requests

- **F3 (`lib/validate.ts`)**: validator 422s answer directly and skip `localizeFields`, so zod field messages (address, card, email) stay English for `da`/`de`/…; VAREL localized them. Route the validator's error through the same localization as `onError`.
- **F4 / I1 (`lib/orders.ts`)**: `nextOrderNumber` runs `MAX(CAST(SUBSTRING(number…)))` over all `shop_orders` per checkout (full scan). Fine at VAREL volume; later a sequence or `ORDER BY id DESC LIMIT 1`.
- **WP-19**: don't hold a long transaction around `refundOrder` (Stripe call); pass reasons `order` / `return-<id>`.
- **WP-14**: customer cancel passes reason `cancel`.
- **WP-22**: `sendTemplate` must never throw (also on `E_JOBS_RATE_LIMITED`); WP-11 wraps every send in try/catch anyway.
- **WP-12**: the checkout UI should call `/site-api/checkout/:number/cancel` when `stripe.confirmPayment` errors, and poll `/sync` every 2 s for 30 s on the confirmation page while `payment === 'Pending'`; use `allowEmbeddedCheckout(Astro.csp, 'stripe')` on the checkout page only when `/checkout/config` says stripe. `src/lib/checkout-transport.ts` / `components/payments/*` (template Buy button) are unused by this checkout.
- **I2**: rate limits on `POST /checkout`, `/:number/sync`, `/:number/cancel` (marked `// I2: rate limit`).

## Known gaps

- Stripe was exercised only with a stubbed `fetch` (no keys may be written to `.env`). Try it in the Preview with the owner's test keys.
- Schedules don't tick locally; the job is covered by calling `expirePending` directly.
